## 結論

`transition-rules.json` の `transition-rule-claim-master-r8-06` が `allowedOptionsByR8ReformStatus["reform-target"]` として既に確定しているoption code 11〜22（新12区分）について、各option codeが対応する平均工賃月額の金額境界を一次資料から一意に確定した。対応は次の決定表のとおりで、**12区分すべてで一意に確定でき、投入を見送った区分は無い**。

#### `reform-exempt`を投入しなかった理由

Task 5で`service-codes.json`へ180行を追記した直後、`ClaimMasterFileValidator.ValidateConditions`の未参照ガードが`r8-reform-status-exempt`に対しても発火することが判明した（`r8-reform-status-target`はTask 4・5が追加した180行の`conditionSelectors`から参照されるため使用済みになるが、`reform-exempt`を参照する行は本フェーズのどこにも無い）。

`reform-exempt`をこの135行のどれかに紐付けようとすると、次の2つの理由でどちらも成立しない。

1. **CLAUDE.mdハード制約・タスク指示の明示的禁止**: 「R6の条件定義を書き換えない。R8はeffectiveFrom: 2026-06の新規追加のみ」。R6行の`conditionSelectors`へ追記することはR6行の書き換えに当たる。
2. **`ClaimMasterFileValidator`のもう一つの機械的な検査**: 実際に1行だけ`r8-reform-status-exempt`（`effectiveFrom: 2026-06`）を試験的に追記したところ、`ValidateConditions`とは別の検査が「`condition 'r8-reform-status-exempt' does not cover the service period`」で拒否した。conditionDefinitionの有効期間（2026-06〜）が参照元の行の有効期間（2024-04〜）を覆っていないと判定されるため、**R6行を書き換えない制約を破らなくても、この特定の組合せは仕組み上ブロックされる**。

新しく`effectiveFrom: 2026-06`の行を作って`reform-exempt`を参照させることも検討したが、本フェーズ（Task 3〜5）はいずれもreform-**target**向けの新12区分だけを対象にしており、reform-exempt向けの新規行を作る根拠となる一次資料上の要求も、ブリーフ上の要求も無い。したがって`reform-exempt`は**投入を見送り**、`r8-reform-status-target`の1トークンだけをseedする。

#### 副次的な発見: `Reform_target_offices_still_fail_closed_on_r6_numeric_bands`のテスト層の訂正

Task 5ブリーフは「改定対象がR6区分option 1〜7・9で2026-06を請求しようとすると例外」という主張を`ServiceCodeResolver.ResolveBasicReward`への直接呼び出しでテストするコードを示していたが、実装を確認したところ**`ServiceCodeResolver`自体はAverageWageBandOptionとR8ReformStatusの整合性を検査しない**（`src/Tsumugi.Domain/Logic/Claim/ServiceCodeResolver.cs`の`Evaluate`メソッドは、行が`r8-reform-status`種別のconditionSelectorを持たない場合、その次元を無条件で一致とみなす）。これを実際に実行して確認したところ、R6行（`r8-reform-status`セレクタなし）はreform-targetコンテキストでも普通に解決し、例外は投げられなかった（`Expected...to be thrown...but no exception was thrown`）。
