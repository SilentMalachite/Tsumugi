# ADR 0051: NetArchTest を採用しない（依存グラフ検査ツールの見送り）

- 状態: 確定（2026-08-15）
- 関連: [ADR 0050](0050-bulk-operations-forbidden.md) / CLAUDE.md ハード制約1

## 結論

依存グラフ検査ツール（NetArchTest 等）を導入せず、現行の反射ベースのアーキテクチャテスト（`ArchitectureTests` 4本、`OfflineComplianceTests` / `AppOfflineComplianceTests`）を維持する。

## 背景

`ArchitectureTests` の依存方向検査、および `OfflineComplianceTests` / `AppOfflineComplianceTests` のオフライン遵守検査は、いずれも `Assembly.GetReferencedAssemblies()` を使い、各アセンブリが直接参照するアセンブリ名を列挙して判定している。`GetReferencedAssemblies()` は**直接参照のみ**を返し、推移的参照（そのアセンブリが参照するアセンブリがさらに参照するアセンブリ）はたどらない。

CLAUDE.md ハード制約1 が「各アセンブリ自身の参照のみ走査、推移閉包は対象外」と明記しているのはこの事実による。`docs/open-questions.md`（「アーキテクチャ/オフラインテストは直接参照のみを検査」、56行目）がこの穴と、依存グラフ全体を検査できるツール（NetArchTest 等）の採否を検討事項として起票していた。

## 決定

見送る。現行の依存方向違反は 0 件であり、`Tsumugi.Domain` / `Tsumugi.Application` / `Tsumugi.Infrastructure` / `Tsumugi.App` の4アセンブリ＋既存4テストという規模に対して、新規 NuGet 依存の追加とルール記述の学習コストが見合わない。

## 選択肢

### A: NetArchTest を採用する（不採用）

依存グラフを推移的にたどるルールを NetArchTest で記述できるが、新規 NuGet 依存が増える。CLAUDE.md ハード制約1（オフライン専用）の検査対象そのものが増えることにもなり、依存追加の是非を慎重に検討する必要がある一方、現時点で違反は0件であり急ぐ理由がない。不採用。

### B: 自前で `GetReferencedAssemblies()` を BFS して推移閉包を張る（不採用）

外部依存を増やさずに推移的参照を検査できる案。しかし `System.*` や `Microsoft.*` の BCL アセンブリまで到達するため、除外リストの調整（偽陽性の抑制）が必要になり、S2（本スライス）の射程を超える。不採用。

### C: 見送り（採用）

現行の反射ベースのアーキテクチャテストを維持し、直接参照のみの検査を続ける。

## 影響

### 残る限界

推移的参照は依然として未検査のままである。プロダクションアセンブリが直接参照していないが推移的に取り込まれるアセンブリ（例: 直接参照するライブラリがさらに通信APIを持つライブラリを参照する場合）は、依存方向検査・オフライン検査のどちらでも検出できない。

### 再検討トリガ

次のいずれかが起きた時点で、本 ADR を見直す。

1. **プロダクションアセンブリが第三者ライブラリを新規に直接参照し、推移閉包を目視で追えなくなったとき。** 現在は依存する第三者ライブラリの数が少なく人手での確認が現実的だが、依存が増えると機械検査の必要性が高まる。
2. **依存方向違反が実際に本番コードへ1件でも混入したとき。** 直接参照の検査をすり抜けて推移的参照経由の違反が発生した実例が出れば、選択肢Bまたは NetArchTest 採用を再検討する具体的な根拠になる。
3. **S5（配布）で self-contained 発行の内容物検証に同じ機構を再利用できるとき。** 配布パッケージングの段階では発行済みバイナリの内容物を検査する必要が生じうるため、その検査基盤と依存グラフ検査を共通化できるなら、導入コストの見合いが変わる。
