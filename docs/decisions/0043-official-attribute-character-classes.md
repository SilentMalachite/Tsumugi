# ADR 0043: 属性区分に基づく文字種の強制と、項目の内容欄の優先

- 状態: 確定（2026-07-25）
- 関連: [ADR 0024](0024-kokuhoren-csv-and-field-mapping.md) / [ADR 0033](0033-csv-official-spec-conformance-from-registered-sources.md) /
  [ADR 0037](0037-mechanical-item-table-extraction.md) / [ADR 0038](0038-row-level-evidence-for-csv-spec.md)

## 結論

1. CSV 仕様の各項目は**公式の属性区分**（`英数` / `数値` / `コード値` / `漢字`）を運用 spec に持ち
   （`officialAttribute`）、`CsvCellEncoder` が区分ごとの文字種規則を強制する。区分の値は ADR 0037 の
   機械抽出と**完全一致**でなければならない（`ItemTableCrossCheckTests`）。
2. **支給決定者氏名カナ（`provider:J121:01:008`）は半角カナで出力する。** 公式属性が `英数`
   （半角 1 バイト）であり、全角カナのままでは仕様違反だった。全角入力は出力時に半角へ写し、
   半角形を持たない文字（ひらがな・漢字・康熙部首など）は丸めずに fail-close する。
3. 属性区分の一般規則は「**特に記載が無い限り**」の前置きつきで定められているため、
   **項目の内容欄に個別の指示がある項目はその指示が優先する**。コントロールレコードの
   市町村番号 `0` は公式指示どおりであり、「コード値属性の全桁 0 は未設定＝必須項目ならエラー」
   という一般規則をこの項目に当てる guard は**置かない**。

## 背景

Phase 3-3 の残課題として「属性区分に基づく文字種規則の強制」と「コントロールレコードの
市町村番号の設定値」が未解決だった（`docs/open-questions.md`）。いずれも公式システムでの
取込失敗に直結しうる。登録済み一次資料 `common-r7-10`（SHA-256 `f6932c52…`、2026-07-25 に
登録 URL から再取得して一致を確認）を読み直して確定した。

**節番号の訂正**: open-questions は「共通編 1.2.3③」と記していたが、属性区分を定めるのは
**1.3.2(1)③（物理 10〜11 頁）**である。1.2.2(3)/(4)（物理 8 頁）は文字コードと特記事項の節。

### 条文（原文引用は証跡台帳 `spec-evidence-r7-10.json` に置く）

- 前置き（物理 10 頁）: 「特に記載が無い限り、以下の形式でデータを設定することを表す。」
- `英数`: 「半角の英字、数字、カナ文字１文字をそれぞれ 1 バイトで表す。半角の英小文字は使用できない。」
- `数値`: 「0，1，2，～，9 の数字 1 桁をそれぞれ 1 バイトで表す。マイナスの数字の場合は左側に半角のマイナス（"-"）を付加する。」
- `コード値`: 「0，1，2，～，9 の数字 1 桁をそれぞれ１バイトで表す。」
  ※1「"0" が 1 桁以上、最大桁以下で設定されている場合は未設定として取り扱う。」
  ※2「必須項目が未設定の場合（※１により未設定として取り扱う場合を含む）はエラーとする。」
- `漢字`: 「漢字 1 文字をそれぞれ 2 バイトで表す。」
- 物理 11 頁: 「「英数」項目には漢字（2 バイトコード）を混在させない。」
  「「漢字」項目には半角の英字、数字、カナ文字（1 バイトコード）を混在させない。」
- 物理 6 頁 コントロールレコード 項番 6: 「送付元または送付先が市町村の場合は市町村番号を設定、
  市町村以外の場合は 0 を設定する」（項番 7 事業所番号・項番 8 都道府県番号も同じ形）

### 見つかった仕様違反

`provider:J121:01:008 支給決定者氏名カナ` は属性 `英数` なのに `Recipient.KanaName` をそのまま
出力しており、全角カナ氏名が CSV に載っていた（golden `csv-golden-cjk.csv` に
`"ツムギタロウ"` として固定されていた）。桁数 `25`（**奇数**）も 1 バイト／文字の項目であることを
裏づける（2 バイト／文字なら奇数長になりえない）。

## 選択肢

### (a) 属性区分をどこに置くか

| 案 | 内容 | 判断 |
|---|---|---|
| A-1 | 運用 spec の項目定義に `officialAttribute` を持たせ、抽出結果と完全一致で突合する | **採用**。新しい施行分で属性が変われば突合が RED になり、encoder の挙動が変わる前に人が判断する |
| A-2 | 抽出結果（`*-item-tables.json`）を実行時に join して属性を得る | 不採用。運用 spec と抽出結果という 2 枚の突合が消え、属性が変わると**黙って挙動が変わる** |
| A-3 | `dataType` から属性を推定する | 不採用。`text` は `英数` と `漢字` の両方に対応し、写像が一意でない |

### (b) 全角カナ氏名をどうするか

| 案 | 内容 | 判断 |
|---|---|---|
| B-1 | 出力時に半角へ写す（`modelPath` に `:halfWidthKana` を宣言） | **採用**。氏名カナは定義上カナなので、半角化が仕様を満たす唯一の道。帳票（PDF）は全角のまま |
| B-2 | 全角を fail-close し、入力を半角カナに限る | 不採用。既存データが出力不能になり、画面表示にも半角カナを強いる |
| B-3 | 全角のまま出す（現状維持） | 不採用。「英数項目に 2 バイトコードを混在させない」に反する |

### (c) 半角化の写像表

| 案 | 内容 | 判断 |
|---|---|---|
| C-1 | Unicode の互換分解（NFKD）から逆引き表を実行時に導出する | **採用**。手書きの 80 行超の表を持たず、濁音・半濁音も基底＋結合文字として自然に扱える |
| C-2 | 変換表を C# に手書きする | 不採用。写し間違いの余地があり、レビューできる量でもない |
| C-3 | `Microsoft.VisualBasic.Strings.StrConv` | 不採用。Windows 専用でクロスプラットフォーム要件（ハード制約6）を満たさない |

### (d) コード値属性の「全桁 0 は未設定」を一律に強制するか

一律に強制すると、必須項目である市町村番号・都道府県番号に公式が指示する `0` を出せなくなる。
属性区分は「特に記載が無い限り」の一般規則なので、**項目の内容欄が優先する**。一律 guard は置かず、
その判断根拠を証跡台帳の `rule:item-note-overrides-attribute-default` に残す。

## 決定

- `CsvFieldSpecification.OfficialAttribute` を必須にする（443 項目すべてが宣言しないと spec の
  読み込み自体が落ちる）。同期は `build/sync_official_attributes.py`。
- `CsvOfficialAttribute` が 4 区分の閉じた語彙と文字集合を持ち、`CsvCellEncoder` が
  `InvalidCharacterForOfficialAttribute` / `UnknownOfficialAttribute` で fail-close する。
  検証は CP932 変換の**後**に置く（表現不能文字は属性違反ではなく別の理由で落とす）。
- `英数` の許容文字は「半角英大文字・数字・半角カナ」＋**スペースと二重引用符**。後者 2 つは
  1.2.2(4) のデータ設定例が英数項目に含めているため許す（`XY Z` / `"KLM"`）。
- `数値` はマイナス符号を許さない。仕様は許すが、どの項目が負値を取り得るかは項目単位で
  宣言されておらず、本アプリの生成器は負値を出さない。**狭い側に寄せて fail-close** する。
- `漢字` は「半角の英字・数字・カナ文字」を含むと fail-close（記号・全角は許す）。
- 氏名カナは `modelPath: "Recipient.KanaName:halfWidthKana"`。単位接尾辞の閉じた語彙
  （`ClaimCsvModelPath.KnownUnitSuffixes`）に `halfWidthKana` を追加する。
- コントロールレコードは `006` 市町村番号 `0` / `007` 事業所番号＝自事業所 / `008` 都道府県番号 `0`
  のまま（変更なし）。根拠を証跡台帳へ登録し、`OfficialAttributeConformanceTests` で固定する。

## 影響

- **B 型請求の CSV は全項目が 1 バイト文字になった**。2 バイトを載せられる項目は属性 `漢字` の
  2 項目（`provider:J121:03:011` 摘要 / `provider:J611:02:035` 備考）だけで、どちらも確定
  snapshot に含まれず常に空欄（ADR 0032 の既知の限界）。したがって CP932 の 2 バイト変換・
  引用規則は実データ経路では働かず、`CsvCellEncoder` の単体テストが担保する。
- golden は `csv-golden-cjk.csv` のみ変化（`"ツムギタロウ"` 14 バイト → `ﾂﾑｷﾞﾀﾛｳ` 7 バイト。
  ファイル 1815 → 1808 バイト）。他 3 種は fixture が既に半角カナのため不変。
- 康熙部首の fail-close 理由が `NonRepresentableCharacter` → `UnresolvableModelPath` に変わる
  （半角化の段が CP932 変換より前に立つ）。fail-close する事実は変わらない。
- Unicode 正規化（NFKD）に依存する。正規化は Unicode の安定性ポリシーで保証されるため
  macOS / Windows で同じ結果になるが、**依存していること自体は記録に残す**。
- 残る未実装: なし（open-questions の該当 2 件はクローズ）。属性区分と `dataType` の対応表
  （`ItemTableCrossCheckTests.DataTypesByOfficialAttribute`）は引き続き 1 段目の網として働く。
