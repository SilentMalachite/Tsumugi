# 0037 一次資料の項目表を機械抽出して運用 spec と突合する

- 状態: 採用（2026-07-25）
- 関連: ADR 0024（国保連CSVと項目マッピング）/ ADR 0033（登録済み一次資料からの仕様適合）/ ADR 0036
- 一次資料: `provider-r7-10`（インタフェース仕様書 事業所編、SHA-256 `44e94a7817bde2b9…`、340頁）

## 結論

運用 spec（`provider-claim-r7-10.json`）を人の書き起こしだけに依存させない。
インタフェース仕様書の**項目表を罫線からセル単位で機械抽出**して checked-in し
（`provider-r7-10-item-tables.json`）、突合テストで書き起こし誤りを機械検出する。

## 背景

Phase 3-3 の後半に見つかった誤りは、いずれも「誰かがもう一度 PDF を読んだ」ときにしか
見つからなかった:

| 誤り | 一次資料の記載 |
|---|---|
| `provider:J611:02:027` に分をそのまま出力（単位誤り） | 「実際にサービス提供した時間数（**時間**）を整数部2桁＋小数部2桁で設定、例：1.5時間→0150」 |
| `provider:J121:04:009` と `:02:010` を同値扱い | 前者「**欠席時対応加算等も**1日とカウントする」／後者「**欠席時対応加算は除く**」 |
| `provider:J121:05` を「経過措置」と誤解 | 「05 を設定する（**契約情報**レコード）」 |
| 地域区分コードを級地番号のゼロ詰めで出力 | 共通編コード一覧「11:一級地〜17:七級地／23:その他」 |

いずれも**項目表の「項目の説明」欄に書かれていた**。つまり書き起こし時点で説明文を
保持していれば機械的に突合できた。

制度マスタ側（`ClaimMasters/Seed/*.json`）は行単位に `effectiveFrom` と `sourceRefs`
（documentId＋sha256＋locator＋supports）を持つ成熟した形になっているが、CSV 仕様側は
`sourcePage` の記載だけで、値そのものの裏付けが無かった。

## 決定

1. **抽出はヒューリスティックにしない。** 対象の表は罫線で囲まれているので、
   ページの描画命令から水平・垂直罫線を集め、その交差でセルを決める
   （`build/extract_interface_item_tables.py`）。
   - 表ヘッダ（項番／項目名／属性／ﾊﾞｲﾄ数／説明・内容／備考）はページによって
     1〜3 行帯に割れ、「項番」が「項」「番」の 2 語に分かれる頁もあるため、
     **列ごとに結合した文字列**で判定する。
   - 項目名欄が「群ラベル｜個別名」に分かれる表（集計欄）では、群ラベルは行結合された
     **縦書き**セルで、頁の途中から始まる仕切り線で区切られる。仕切りは行ごとに適用する。
   - 文字幅は公式表記のまま保つ（例「１割相当額」は全角）。数値として読む列だけ NFKC で寄せる。
2. **抽出は登録済み文書に紐づける。** PDF の SHA-256 が `sources.json` の登録値と
   一致しなければ fail-close する。抽出結果は `sourceSha256` を持ち、突合テストが
   登録値との一致を固定する。
3. **突合テスト**（`ProviderItemTableCrossCheckTests`）が固定するもの:
   項番集合／桁数（424 項目）／項目名（個別名が運用 spec の項目名に含まれること）／
   公式属性区分が 4 値のいずれか／属性区分と `dataType` の対応／説明文が空でないこと。
4. **PDF はリポジトリに置かない。** 抽出結果だけを checked-in し、テストは PDF 無しで動く。
   再生成は `sources.json` の URL から取得した PDF で行う。

## 影響

- 事業所編の 9 レコード・**424 項目**（全 443 項目の 96%）を突合対象にした。
  現状の突合結果は**全項目一致**（桁数 424/424、項目名 424/424、属性と dataType の整合 424/424）。
- 新しい施行分が出たときの作業は「340 頁を読み直す」から
  「抽出結果を再生成して差分をレビューする」に変わる。
- 公式の**属性区分**（英数／数値／コード値／漢字）が全項目について機械可読になった。
  観測された対応は 数値→numeric（241）／コード値→code・date・yearMonth（144）／
  英数→text（37）／漢字→text（2）。共通編 1.2.3③ の文字種規則（英数属性は半角小文字不可 等）を
  エンコーダで強制する作業はこの上に載せられる（`docs/open-questions.md` で追跡）。
- 歯の確認: 運用 spec の 1 項目に「桁数の誤り・属性との不整合・項目名の誤り」を入れると
  3 テストが項目 ID 付きで RED になることを確認した。

## 追記（2026-07-25）: 共通編（1 頁 3 表）に対応した

共通編のレコードフォーマットはコントロール／データ／エンドの **3 表が同じ頁（物理 6 頁）に並ぶ**。
表単位のアンカーとして、spec の record に `sourceTableCaption`（例「・コントロールレコードフォーマット」）を
持たせ、抽出器は「見出しの直下にあるヘッダ行から、次のヘッダ行の手前まで」を 1 表として読む。

実装中に 2 つの落とし穴を踏んだ（どちらも 1 頁複数表でしか出ない）:

1. **キャプションの部分一致で節見出しに誤マッチ**した。「レコードフォーマット」（節見出し）が
   「・データレコードフォーマット」の部分文字列になるため、3 表すべてが最初の表になった。
   → 見出しの**全文**を含む語だけを採る。
2. **ヘッダ探索が表境界をまたいだ**。表と表の間の空き帯を起点にすると次の表のヘッダを巻き込み、
   ヘッダ位置が 1 帯早くずれて（項番欄が「１２項番」のような文字列になり）表の選択が壊れた。
   → 項番列は**完全一致**を要求し、かつヘッダ候補は**先頭の行帯に見出し語がある**ことを要求する。

事業所編の抽出結果はこの変更で 1 バイトも変わらないことを確認済み（回帰なし）。

### 共通編で見つかった 2 件の差分（いずれも理由つきで宣言）

| 項目 | 差分 | 扱い |
|---|---|---|
| `common:outer:control:003` | 公式表は「ボリュ－ム通番」と**全角ハイフンマイナス (U+FF0D)** で組まれている。spec は長音符 (U+30FC) へ正規化している | 突合テストの `DeclaredNameDifferences` に理由つきで宣言。文書が変われば再確認する |
| `common:outer:data:003` | ペイロードは可変長で、公式表は**属性・ﾊﾞｲﾄ数を空欄**にしている。spec の 822 は導出値 | `DeclaredMissingByteLengths` に宣言し、導出の根拠を証跡台帳（ADR 0038）へ `derived-byte-length` として登録 |

### 波及

- 突合対象は **事業所編 424 項目＋共通編 19 項目 = 443 項目（全項目）**。
- `generatorRule` の `source=doc:pNN:itemNN` アンカーは **372 件すべてが検証対象**になった
  （それまで共通編分 17 件は未検証だった）。
- 証跡台帳の `knownGaps` が 3 件 → 2 件になった。

## 残り（この ADR の範囲外）

- 行単位の `sourceRefs`（ADR 0038 で導入済み）、CSV 仕様の複数版共存（ADR 0039 で導入済み）、
  pass-through 項目の汎用入力化は別の増分。
